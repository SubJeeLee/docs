## **\[컴퓨터 네트워크\] 2장: 애플리케이션 계층 (Application Layer)**

### **1. 애플리케이션 계층의 원리**

**클라이언트-서버 패러다임 (Client-Server Paradigm)**

- **서버 (Server):** 항상 켜져 있는 호스트로, 영구적인 IP 주소를 가집니다. 서비스 확장을 위해 주로 **데이터 센터**에 위치합니다.
- **클라이언트 (Client):** 서버와 통신하며, 간헐적으로 연결될 수 있고 동적 IP 주소를 가질 수 있습니다. 클라이언트끼리는 직접 통신하지 않습니다.

**피어 투 피어 (P2P) 아키텍처**

- 항상 켜져 있는 서버가 없으며, 임의의 종단 시스템(peers)끼리 직접 통신합니다.
- **자가 확장성(Self-scalability):** 새로운 피어가 참여하면 서비스 능력과 수요가 동시에 늘어나는 특징이 있습니다. 관리가 복잡하다는 단점이 있습니다.

**전송 프로토콜 서비스 (TCP vs UDP)**

애플리케이션은 용도에 따라 적절한 전송 서비스(Transport Service)를 선택해야 합니다.

- **TCP:** 신뢰할 수 있는 데이터 전송, 흐름 제어(수신자 과부하 방지), 혼잡 제어(네트워크 과부하 시 전송량 조절)를 제공하며 연결 지향형(Connection-oriented)입니다.
- **UDP:** 신뢰할 수 없는 데이터 전송을 제공하며, 혼잡/흐름 제어, 연결 설정 과정이 없습니다.
- **UDP를 사용하는 이유:** 설정 과정이 없어 빠르고 단순하기 때문입니다. 실시간 오디오/비디오처럼 약간의 손실을 감수하더라도 속도가 중요한 앱에서 주로 사용합니다.

### **2. 웹과 HTTP (Web and HTTP)**

**HTTP 개요**

- **무상태 프로토콜 (Stateless Protocol):** 서버는 클라이언트의 과거 요청에 대한 정보를 유지하지 않습니다. 상태를 유지하는 프로토콜은 복잡하고 관리가 어렵기 때문입니다.

**비지속 및 지속 HTTP**

- **비지속 HTTP (Non-persistent):** 한 번의 TCP 연결에 하나의 객체만 전송합니다. 각 객체당 **2 RTT**(왕복 시간)와 파일 전송 시간이 소요됩니다.
- **지속 HTTP (Persistent):** 한 번의 TCP 연결로 여러 객체를 전송할 수 있어 서버 부하와 응답 시간을 줄입니다.

**쿠키 (Cookies)**

HTTP의 무상태성을 보완하기 위해 사용합니다. 응답 메시지의 `Set-cookie` 헤더와 요청 메시지의 `Cookie` 헤더를 통해 상태를 유지합니다.

- **퍼스트 파티 쿠키:** 사용자가 직접 방문한 사이트에서 설정한 쿠키입니다.
- **서드 파티 쿠키:** 사용자가 방문하지 않은 광고 서버 등에서 설정한 쿠키로, 여러 사이트에 걸친 사용자 행동 추적에 사용됩니다.
- **GDPR (유럽 개인정보보호법):** 쿠키를 통해 개인을 식별할 수 있는 경우 개인정보로 간주하며, 사용자는 쿠키 허용 여부에 대해 **명시적인 통제권**을 가집니다.

**웹 캐시 (Web Cache, 프록시 서버)**

- **필요성:** 클라이언트 응답 시간 단축, 기관의 접속 링크 트래픽 감소, 콘텐츠 제공 효율성 향상을 위해 사용합니다.
- **조건부 GET (Conditional GET):** 캐시된 객체가 최신인지 확인하기 위해 `If-modified-since` 헤더를 사용합니다. 변경되지 않았다면 서버는 데이터 없이 `304 Not Modified` 응답만 보냅니다.

**HTTP/2와 HTTP/3**

- **HTTP 1.1의 문제점:** 여러 객체를 요청할 때 선입선출(FCFS) 방식으로 처리되어, 큰 객체 뒤의 작은 객체가 기다려야 하는 **HOL(Head-of-Line) 블로킹** 현상이 발생합니다.
- **HTTP/2 개선점:** 객체를 프레임 단위로 나누고 전송 순서를 섞는 **프레임 인터리빙**을 통해 HOL 블로킹을 완화하고, 우선순위 기반 전송과 서버 푸시 기능을 도입했습니다.
- **HTTP/3:** HTTP/2가 여전히 TCP 자체의 손실 복구 메커니즘으로 인해 발생하는 지연 문제를 해결하기 위해, TCP 대신 **UDP 기반의 QUIC** 프로토콜을 사용합니다. QUIC은 보안 기능과 객체별 오류/혼잡 제어를 제공하며 훨씬 빠른 연결 설정(0-RTT/1-RTT)이 가능합니다.

### **3. 인터넷 이메일**

- **주요 구성 요소:** 사용자 에이전트(UA), 메일 서버, **SMTP** 프로토콜.
- **SMTP (Simple Mail Transfer Protocol):** 메일 서버 간 메시지를 전송하는 프로토콜로, **TCP(포트 25)**를 사용하며 지속 연결을 지원합니다.
- **특징:** 모든 메시지는 7비트 ASCII여야 하며, 메시지의 끝은 `CRLF.CRLF`로 구분합니다.
- **메일 액세스 프로토콜:** 서버에 저장된 메일을 가져오기 위해 **IMAP**(메시지 관리 및 삭제 가능)이나 HTTP(웹 기반 메일)를 사용합니다.

### **4. DNS (Domain Name System)**

**DNS의 구조**

중앙 집중화 방식은 단일 실패 지점, 과도한 트래픽, 유지보수 문제로 인해 **확장성이 없어** 사용하지 않습니다. 대신 전 세계에 분산된 계층적 데이터베이스 구조를 가집니다.

1. **루트 DNS 서버:** TLD 서버의 주소를 알려주는 최상위 서버입니다.
2. **TLD (Top-Level Domain) 서버:** .com, .org, .kr 같은 상위 도메인을 담당합니다.
3. **책임(Authoritative) DNS 서버:** 특정 조직의 호스트 이름과 IP 매핑 정보를 실제로 가진 서버입니다.
4. **로컬 DNS 서버:** 호스트가 쿼리를 보낼 때 가장 먼저 만나는 서버로, 캐시를 확인하거나 계층 구조에 질문을 전달합니다.

**DNS 쿼리 방식**

- **반복 쿼리 (Iterative Query):** 질문을 받은 서버가 "나는 모르지만 이 서버에게 물어봐"라며 다음 단계 서버의 주소를 알려줍니다.
- **재귀 쿼리 (Recursive Query):** 질문을 받은 서버가 직접 다음 서버에 물어봐서 최종 답변을 가져와 전달합니다.

**정보 캐싱 및 레코드**

- 한번 얻은 정보는 일정 시간(**TTL**) 동안 캐싱하여 응답 속도를 높입니다.
- **DNS 레코드 종류:** `A`(호스트명-IP), `NS`(도메인-책임서버명), `CNAME`(별칭-정식명칭), `MX`(메일 서버).

**DNS 보안**

- **DDoS 공격:** 루트 서버나 TLD 서버에 트래픽을 폭격합니다.
- **스푸핑/캐시 포이즈닝:** 쿼리를 가로채 가짜 응답을 주거나 캐시에 잘못된 정보를 심는 공격입니다. 이를 방지하기 위해 인증 기능을 더한 **DNSSEC**가 사용됩니다.

### **5. 비디오 스트리밍과 CDN**

**비디오 스트리밍 기술**

- **코딩(압축):** 이미지 내 중복성을 이용하는 **공간 코딩**과 프레임 간 차이만 기록하는 **시간 코딩** 기술을 사용합니다.
- **비트레이트:** **CBR**(고정 속도)과 장면의 복잡도에 따라 속도가 변하는 **VBR**(가변 속도) 방식이 있습니다.
- **스트리밍의 어려움:** 가변적인 네트워크 대역폭과 **지터(Jitter, 불규칙한 도착 시간)**가 문제이며, 이를 해결하기 위해 클라이언트 측에서 **플레이아웃 버퍼**를 사용합니다.

**DASH (Dynamic, Adaptive Streaming over HTTP)**

네트워크 환경에 맞춰 비디오 화질을 동적으로 조절하는 기술입니다. 서버는 비디오를 여러 화질(비트레이트)의 조각으로 나누어 저장하고 **매니페스트 파일**을 제공하며, 클라이언트가 자신의 대역폭에 맞는 최적의 화질을 선택해 요청합니다.

**콘텐츠 전송 네트워크 (CDN)**

수많은 사용자에게 효율적으로 스트리밍하기 위해 전 세계에 서버(노드)를 분산 배치합니다.

- **배치 전략:**
  - **Enter Deep (Akamai 방식):** 수많은 접속 네트워크 내부 깊숙이 서버를 배치하여 사용자에게 최대한 가깝게 가져갑니다.
  - **Bring Home (Limelight 방식):** 적은 수의 거대한 서버 클러스터를 접속 네트워크 인근 지점(POP)에 배치합니다.
- **넷플릭스 사례:** 자사 CDN인 **OpenConnect** 노드에 콘텐츠를 복제해두고, 사용자의 요청이 오면 매니페스트 파일을 통해 최적의 노드에서 DASH 방식으로 스트리밍합니다.

### **6. 소켓 프로그래밍 (Socket Programming)**

- **소켓:** 애플리케이션 프로세스와 전송 프로토콜 사이의 "문" 역할을 합니다.
- **UDP 소켓:** 연결 설정이 없으며, 데이터를 보낼 때마다 목적지 IP와 포트 번호를 명시해야 합니다.
- **TCP 소켓:** 서버가 먼저 "환영 소켓(Welcoming socket)"을 열고 기다려야 하며, 연결 설정 과정을 통해 두 프로세스 간의 전용 파이프가 형성됩니다.
- **타임아웃:** 네트워크 지연으로 무한정 대기하는 것을 막기 위해 `settimeout()`과 `try-except` 구문을 사용하여 예외 처리를 합니다.

### **2장 요약 및 핵심 정리**

- **애플리케이션 아키텍처:** 클라이언트-서버 vs P2P.
- **전송 서비스 모델:** 신뢰성의 TCP vs 비신뢰성의 UDP.
- **주요 프로토콜:** HTTP(웹), SMTP/IMAP(메일), DNS(이름 변환).
- **현대 기술:** 비디오 스트리밍(DASH), CDN, 그리고 진화된 HTTP/3(QUIC).
- **핵심 가치:** 분산 시스템의 확장성과 네트워크 엣지에서의 복잡성 관리.
